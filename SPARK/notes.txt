## SPARK ARCHITECTURE
It follows Master-Slave Architecture
A cluster has multiple nodes and each node has a role of master or slave
Spark distributes the data and computations across multiple nodes in the cluster,
allows parallel processing

one of the node acts as a master node and the rest are slave nodes
                                          -------- WORKER NODE
DRIVER PROGRAM                           |          EXECUTOR | CACHE
SPARK CONTEXT  ----------> CLUSTER MANAGER            TASK     TASK 
                                         |
                                         |--------WORKER NODE 
                                                 EXECUTOR | CACHE
                                                 TASK     TASK
When a user submits an application, the cluster manager allocates resources and starts executors on worker nodes.
one node acts as a driver node and the rest are worker nodes.
a resource manager is responsible for allocating resources which will be installed on each node.

for example we have 10 nodes in a cluster
each node has a executor installed on it.
having 64 gb ram and 16 core per node

Total ram = 10 * 64 = 640 gb
Total cores = 10 * 16 = 160 cores
suppose we need a driver with 8 gb ram and 2 cores and we need 5 executors with 16 gb ram and 4 cores each
remaining resources = 640 - 8 - (5 * 16) = 640 - 8 - 80 = 552 gb ram
remaining cores = 160 - 2 - (5 * 4) = 160 - 2 - 20 = 138 cores


Driver program calls the main application
SparkContext is created which is the entry point of spark functionality
It would communicate with cluster manager to request resources (CPU, Memory) whose job is to allocate executors in worker nodes
Cluster manager will allocate resources to the driver program

Driver has components like DAG Scheduler, Task Scheduler, and Job Scheduler
Cluster Manager would send status and details of executors to the driver program
Then driver would schedule job. It would take RDD(resilient distributed dataset) and break it into tasks and schedule them on executors
Translate into execution graph called DAG (Directed Acyclic Graph)


RDD 
Resilient Distributed Dataset
It is the main object in Spark
It is an immutable distributed collection of elements
It is fault-tolerant
It is lazily evaluated
The dataset is nothing but the data that we provided.
The distribution means the input data is stored across all worker nodes.
Resilient means if any data is lost, it can be recovered from the original source.

### Corrupted Record 
Corrupted record is a record that is not in the correct format.
we have 3 modes to handle corrupted records:
1. PERMISSIVE - All invalid fields are set to null
2. DROPMALFORMED - Drop the entire record if any invalid field is found
3. FAILFAST - Throw an exception if any invalid field is found


### How can we print Bad records
> first we need to make schema with null values allowed
> then we need to read the file with the schema
> then we need to filter the bad records
> finally we need to print the bad records

from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DoubleType
bad_schema = StructType([
    StructField("ID", IntegerType(), True),
    StructField("name", StringType(), True),
    StructField("age", IntegerType(), True),
    StructField("salary", DoubleType(), True),
    StructField("corrupted_record", StringType(), True)

> truncate = False means it will not truncate the output


> Store bad records in a separate file

### TRANSFORMATIONS IN PYSPARK
1. Narrow Dependency Transformations
> These transformations create a one-to-one relationship between the input and output partitions.
> Examples: map(), filter(), flatMap(), union(), select(), etc.
We dont have to depend on other partitions.
for example, if we have 4 partitions and we apply map() transformation, each partition will be processed independently.

ID NAME AGE INCOME SOURCE
1 John 25 50000 Job
2 Jane 30 60000 Teaching
3 Bob 35 70000 Freelancing
4 Alice 28 55000 Teaching
5 Charlie 40 80000 Youtuber
6 David 32 65000 Job

> Show me people with income > 60000
df.filter(df.income > 60000).show()
> if our data is 200MB and hdfs has 128 MB block size, then it will be stored in 2 blocks
> when we read this data, it will be read in parallel


2. Wide Dependency Transformations
> These transformations create a many-to-one or one-to-many relationship between the input and output partitions.
> Examples: groupBy(), join(), Distinct() etc.
We have to depend on other partitions.
for example, if we have 4 partitions and we apply groupBy() transformation, each partition will be processed based on the other partitions.

> Find the total income of each employee 
df.groupBy("name").sum("income").show()
if data is present in each other executor, then it will be processed based on the other executors as it will
be swapped across executors that will be an expensive operation.

### RDD Resilient Distributed Dateset
Just like List is a data structure [1,2,3,4,5] in python,
RDD is a data structure in spark which is immutable, distributed and fault-tolerant.
It is the fundamental data structure of spark.
It helps in parallel processing of data.
RDD is immutable 
RDD transformation is lazy evaluation
RDD actions trigger the execution
Why rdd is fault tolerant?
> RDDs are fault tolerant because they track the lineage of operations that created them.
> If a partition is lost, it can be recomputed from the original data using the lineage information.
Disadvantages of RDD:
> RDD is immutable
> RDD is not optimized for small records
> RDD is not optimized for iterative algorithms
> RDD is not optimized for columnar storage
> RDD is not optimized for in-memory computing
So it was replaced by Dataframe and Dataset APIs. Better to use Dataframe and Dataset APIs.

Dataframe
data.groupBy("column_name").count().show()

SQL
SELECT column_name, COUNT(*) FROM table_name GROUP BY column_name

RDD 
data.map(lambda x: (x[0], 1)).reduceByKey(lambda x, y: x + y).collect()

> Dataframe is optimized for small records
> Dataframe is optimized for iterative algorithms
> Dataframe is optimized for columnar storage
> Dataframe is optimized for in-memory computing
# In modern spark versions, RDD is not used much as dataframe  is converted to RDD internally

##### PARQUET #####
There are two types of orientation:
1. Row-oriented
> Data is stored in rows, where each row represents a complete record.
for example:
Name, Age, City
John, 25, New York
Jane, 30, Los Angeles
it will be stored as:
John, 25, New York
Jane, 30, Los Angeles

> Row-oriented is good for transactional systems where you need to read entire rows of data.
> But it is not good for analytical systems where you need to read only a few columns of data.


2. Column-oriented
> Data is stored in columns, where each column represents a single attribute.
for example:
Name, Age, City
John, 25, New York
Jane, 30, Los Angeles
it will be stored as:
Name: John, Jane
Age: 25, 30
City: New York, Los Angeles

> Column-oriented is good for analytical systems where you need to read only a few columns of data.
> But it is not good for transactional systems where you need to read entire rows of data.

OLAP VS OLTP
OLAP: Online Analytical Processing
> Used for complex queries and analysis
> Optimized for read-heavy workloads
> Data is typically stored in a star/snowflake schema
> Examples: Data warehouses, business intelligence, reporting
> Here we have to use SELECT, JOIN, GROUP BY, ORDER BY operations more frequently
> OLAP uses column-oriented storage

OLTP: Online Transaction Processing
> Used for day-to-day operations and transactions
> Optimized for fast, simple queries
> Data is typically stored in a normalized schema
> Examples: Banking systems, e-commerce, customer service
> Here we have to use UPDATE, DELETE, INSERT operations more frequently
> OLTP uses row-oriented storage

# Parquet uses column-oriented storage
> df = spark.read.parquet("path/to/parquet/file")
> df.write.parquet("path/to/parquet/file")
# it is much better for analytical workloads

# CSV uses row-oriented storage
> df = spark.read.csv("path/to/csv/file")
> df.write.csv("path/to/csv/file")
# it is much better for transactional workloads

## PARTITION BY
> it is used to partition the data based on a specific column(s)
> it is useful when you want to organize the data in a specific way
> it is useful when you want to optimize the performance of your Spark application
> it is useful when you want to ensure that the data is evenly distributed across the cluster

df.write.partitionBy("column_name").format("csv").option("header", True).mode("overwrite").save("path/to/csv/file")

df.write.format("csv").option("header",'"true").option("path","path/to/csv/file").partitionBy("column_name").saveAsTable("table_name")

> if there are 200 jobs and  partitions are 100, then each job will have 2 partitions
> if there are 200 jobs and  partitions are 200, then each job will have 1 partition
> if there are 200 jobs and  partitions are 400, then each job will have 2 partitions

### BUCKET BY
> it is used to bucket the data based on a specific column(s)
> it is useful when you want to organize the data in a specific way
> it is useful when you want to optimize the performance of your Spark application
> it is useful when you want to ensure that the data is evenly distributed across the cluster

df.write.bucketBy(3, "column_name").format("csv").option("header", True).mode("overwrite").save("path/to/csv/file")

df.write.format("csv").option("header",'"true").option("path","path/to/csv/file").bucketBy(3, "column_name").saveAsTable("table_name")
3 buckets will be created and data will be distributed across them
if there are 200 jobs and 3 buckets, then each job will have 67 buckets
